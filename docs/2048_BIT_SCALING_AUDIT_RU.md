# Почему прототип не масштабируется до RSA-2048

Дата: 2026-09-29. Объект: исходный архив `rsa-neuro-symbolic-explorer.zip` и импортированный код. Это статический аудит архитектуры, а не измерение успешной факторизации: в текущем окружении PyTorch отсутствовал, checkpoint-файлы не загружались.

## Короткий вывод

Здесь пока нет задачи распараллелить готовый 2048-битный алгоритм. Реализованный метод привязан к 12–16-битным множителям, использует `float64` для самих чисел и перебирает кандидатов последовательно. Параллельный запуск нескольких копий этого кода не восстановит утраченную точность и не придаст модели способность работать с 1024-битными множителями.

## Проверенные блокеры

| Место | Что обнаружено | Следствие |
| --- | --- | --- |
| `solver_api.py`, исходный архив | Ветка `bit_length >= 2048` строила десять искусственных шагов и возвращала `p=q=None`, `oracle_used=True`. | Поиск 2048-битных множителей не выполнялся. При импорте эта ветка стала явным `unsupported`. |
| `TKHD_7_Massive.py` | `MIN_BITS=12`, `MAX_BITS=16`; `MAX_P_VAL=2**16`, `MAX_N_VAL=2**32`. Оракул получает `n/2**32` и умножает выходы на `2**16`. | Числовая шкала зашита в модель и выбор кандидатов. На 2048 бит это не та же задача в увеличенном batch. |
| `torch.float64` и `numpy` | Мантисса float64 имеет 53 значащих двоичных разряда. 2048-битное `N` не помещается в конечное float64; шаг между представимыми числами возле 1024-битного множителя составляет примерно `2**971`. | Целочисленная решётка и проверка соседних кандидатов исчезают задолго до 2048 бит. Нормировка энергии на `sqrt(N)` не исправляет представление самого `N`, `x`, `y`. |
| `CryptoLandscape.energy` | Основная часть `((N-xy)/sqrt(N))**2` равна нулю на всей вещественной гиперболе `xy=N`; штраф `sin²(πx)+sin²(πy)` периодичен и численно теряет смысл на гигантских координатах. | Градиентный спуск сам по себе не указывает на целочисленные делители. Доказательства быстрого перехода к ним в проекте нет. |
| `BATCH_SIZE=16`, `simulate_rays` | Batch состоит из **разных** `N`. В `MDNOracle.get_top_candidates` для каждого элемента отдельно идут 1000 попыток NumPy; затем для каждого элемента выполняется последовательный цикл деления до ±5000 от текущего `x` на шаг. `DataLoader` не настраивает workers. | Есть векторизация части градиентов для нескольких ключей, но нет распараллеливания факторизации **одного** `N`. |
| `test()` | Печатается среднее расстояние до известных `(p,q)` и число вызовов оракула, а не доля точных разложений на отложенных ключах. В архиве нет скрипта обучения checkpoint-файлов. | Текущая метрика не подтверждает ни преимущество над простым делением, ни перенос на другие разрядности. |
| Веб-интерфейс, исходный архив | При отказе бэкенда fallback направлял траекторию к уже известному `key.p`; Python-модуль печатал строку при импорте и ломал `JSON.parse(stdout)`; выражение с `n` в fallback использовало неопределённую переменную. | Показанный «успех» мог быть демонстрацией с известными множителями, а не ответом модели. Fallback удалён, stdout сделан JSON-only. |

### Старые «2048-битные» примеры

Четыре константы `ENTERPRISE_PRIMES` исходного `src/lib/rsa.ts` имели длину **512 или 513 бит**. Произведения пар давали только **1024 или 1025 бит**. Как минимум вторая и третья константы делились на 3, так что не были простыми. У первых трёх различия составляли всего десятки единиц; такая близость также создаёт нерепрезентативные случаи. Демонстрационный `ENTERPRISE_N_LIST` в исходном `solver_api.py` имел 1025 бит и вообще не участвовал в поиске. Эти фикстуры удалены из активного пути генерации.

### Почему больше ядер пока не помогает

Время распараллеленного поиска при фиксированной работе может снижаться максимум примерно пропорционально числу независимых работников, с накладными расходами. Здесь же до распределения работы надо определить **точное целочисленное состояние и проверяемый алгоритм кандидатов**. `batch_size` повышает пропускную способность на наборе маленьких задач, но не уменьшает пространство возможных делителей одного криптографического модуля. Увеличение `NUM_ATTEMPTS`, числа лучей или GPU без контроля вероятности попадания в множитель только масштабирует число попыток.

## Что изменено при импорте

1. `server.ts` передаёт проверенную десятичную строку в Python через `spawn` без shell; ошибка бэкенда больше не выдаёт сырой stderr клиенту.
2. `solver_api.py` возвращает честное `unsupported` для 2048 бит без импорта PyTorch; ложные траектории удалены. Печать устройства перенесена из import в `test()`.
3. `src/App.tsx` не выдаёт отсутствие факторов за успех, проверяет найденные факторы через `BigInt`, не запускает fallback с известным `p`, ограничивает canvas малыми числами и не генерирует ложные большие «ключи».
4. `src/lib/rsa.ts` удаляет составные фикстуры; `vite.config.ts` больше не подставляет `GEMINI_API_KEY` в клиентский bundle.

Это исправления достоверности и базовой безопасности интерфейса. Они **не** создают 2048-битный факторизатор.

## Следующий воспроизводимый эксперимент

1. Восстановить происхождение checkpoint-весов и код обучения. Проверить, что train/test ключи не совпадают, и фиксировать seed, параметры и версии зависимостей.
2. На 16, 24 и 32-битных `N` измерить долю **точных** разложений `p*q=N` на неизвестных заранее примерах, время, число кандидатов и долю решений без оракула. Сравнить с простым точным делением на тех же входах.
3. Для **одного** `N` запустить независимые поисковые задания при 1, 2, 4, 8 workers. Учитывать суммарную работу, накладные расходы и вероятность успеха, а не только wall-clock одного удачного случая.
4. Если метод сохраняет преимущество вне обученной шкалы, определить точное представление больших целых (на CPU или как массивы слов на ускорителе), а затем проверить перенос на возрастающих разрядностях. Без такого промежуточного результата объявлять режим RSA-2048 преждевременно.

Критерий перехода: точные множители для ранее не виденных модулей, независимая проверка `p*q=N`, сравнительная метрика на одинаковом бюджете вычислений и профилирование работы одного `N` на нескольких workers. Отдельно требуется математическое объяснение, почему вероятность попадания в решение не схлопывается с ростом разрядности.
